# v0.4 Packaging, Signing, and Distribution

Version 0.4 ships the WinUI app as MSIX first. The checked-in manifest keeps a development publisher; CI replaces it with the verified signing-certificate subject for signed builds.

## Local Dev Packaging

Use the `winapp` CLI from an elevated Windows shell when installing the dev certificate:

```powershell
winapp cert generate --manifest .
winapp cert install ./devcert.pfx
winapp package <build-output> --cert ./devcert.pfx
```

`winapp cert generate` creates `devcert.pfx` with the default PFX password `password`. Use an HTTPS timestamp service for anything distributed outside local development:

```powershell
winapp package <build-output> --cert ./devcert.pfx --timestamp https://timestamp.digicert.com
```

## CI Packaging

`.github/workflows/package-winui.yml` runs on manual dispatch and on tags matching `v0.4.*`. It builds Release MSIX artifacts for `x64` and `arm64` with package generation enabled and package signing disabled during the build.

For tag builds, the workflow derives both assembly and four-part MSIX versions from the tag (`v0.4.2` becomes `0.4.2` and `0.4.2.0`). Manual runs use the checked-in `0.4.0` development version.

The workflow uses these repository secrets for signed packages:

- `MSIX_SIGNING_CERT_PFX_BASE64`: base64-encoded PFX signing certificate.
- `MSIX_SIGNING_CERT_PASSWORD`: password for the PFX.
- `MSIX_PUBLISHER`: the exact certificate subject, for example `CN=Contoso Software, O=Contoso Software, C=US`.

Manual runs may omit all three values and produce clearly labeled, unsigned validation artifacts retained for three days. Tag builds fail unless all signing values are configured. For a signed build, the workflow verifies that the PFX has a private key, is unexpired, and has a subject exactly matching `MSIX_PUBLISHER`; it then patches the package identity before building. Every `.msix` is signed, timestamped over HTTPS, and verified with `signtool verify /pa` before upload. Tag builds attach only verified signed packages to a draft GitHub release and never auto-publish it.

To create the base64 value on Windows:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('.\release-signing.pfx')) |
    Set-Clipboard
```

Treat unsigned artifacts as packaging diagnostics only. They are not release candidates and should not be distributed.

## Signing Strategy Options

This decision is still open:

- PFX in GitHub secrets: implemented by `package-winui.yml`; easiest first path, but certificate custody depends on repository secret access controls and protected release environments.
- Azure Trusted Signing: preferred long-term path for a public admin tool; requires an Azure tenant, a Trusted Signing account, and `azure/trusted-signing-action`.
- Manual local signing: acceptable for controlled internal distribution or emergency releases, but harder to reproduce and audit.

## Publisher Constraint

The checked-in MSIX `Identity.Publisher` is `CN=DeviceOffboardingManager` for development. Signed CI builds replace it with `MSIX_PUBLISHER` only after confirming that this value exactly equals the PFX subject. Do not permanently paste a production publisher or certificate into source control.

Sideload installs require the signing certificate chain to be trusted on the target machine. For enterprise deployment, Intune can deploy the certificate chain before deploying the MSIX.

## WinGet

Submitting to `microsoft/winget-pkgs` requires a signed installer at a stable public URL. GitHub release assets qualify once the first signed release exists.

Use `wingetcreate` when a signed release asset is available:

```powershell
wingetcreate new <installer-url>
```

## Microsoft Store Checklist

- Partner Center account.
- Age rating questionnaire.
- Privacy policy URL. This is required because the app accesses network and user data.
- Screenshots at 1366x768 or larger.
- Signed MSIX uploaded through Partner Center in a browser. There is no CLI submission path.
